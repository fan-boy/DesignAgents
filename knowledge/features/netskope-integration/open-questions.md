## Resolved
- [x] [Eng] How is a Netskope user tied to a specific Dune person? — **Answer:** Directly, via the same IAM identity (email/UPN) Dune already resolves through SSO/SCIM provisioning, matched against Netskope's own SCIM/SAML-provisioned user record. This is structurally simpler than CrowdStrike's device-login heuristic and is stated explicitly in prd.md.
- [x] [PM] Should Netskope categories be split into a separate score from CrowdStrike and training/simulation inputs, or blended into one score? — **Answer:** Blended into one overall score, for consistency with the CrowdStrike precedent. Carried over by assumption rather than freshly confirmed — flagged above as worth a deliberate re-check now that a second vendor is involved, not fully closed.
- [x] [PM] Should Full Access-only RBAC be reconsidered specifically for Netskope, given SSE/network teams are a more common real-world owner of this credential than SecOps? — **Answer:** No. Stays Full Access-only, matching the CrowdStrike precedent for v1.
- [x] [PM] Should Behavior Confidence (UCI) and the five granular categories be mutually exclusive, or is a soft inline warning the final answer? — **Answer:** Soft warning only, as originally drafted. Admins may enable both if intentional.
- [x] [Both] Is bi-directional write-back to Netskope's UCI (matching Living Security's shipped integration) in scope for any near-term version? — **Answer:** Yes, in scope for v1 — a scope expansion from the original consume-only draft. This introduces a new Share Risk Signals with Netskope flow. Because write-back and Behavior Confidence would otherwise create a circular scoring dependency (Dune signals feed Netskope's UCI, which Dune would then read back in as Behavior Confidence), enabling Share Risk Signals hard-disables Behavior Confidence — this specific combination is blocked, not just soft-warned, unlike the general UCI/granular-category overlap decision above.
